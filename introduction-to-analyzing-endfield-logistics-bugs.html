Preface ​

“Upstream/downstream” usually means adjacent logistics components or factories. Only explicit references to an “upstream/downstream factory” mean the factory at the end of a component chain. Logistics components include belts, pipes, Splitters, Convergers, etc.; factories include Protocol Stashes, Refining Units, Packaging Units, etc. (excluding Reactor Crucibles, Purification Units, the Protocol Automation-Core, and Depot Loaders/Unloaders).

This article presents current research on bugs caused by Endfield's underlying logic. Each section first presents a phenomenon or question, then introduces the rules needed to explain it when they become relevant. The many necessary experiments are omitted; conclusions are given directly.

Gray body text is less important, usually aimed at readers already familiar with Endfield logistics bugs rather than newcomers.

Layering Theory and Output Lag ​

Start with a phenomenon. Connect a fixed-length belt downstream of a Splitter and let it output several items continuously: it suddenly pauses, then continues. This is called output lag.
Experiments show that stall frequency relates to the length of the red-boxed belt: one stall occurs for every 4n items passing through.

We can infer that when an upstream component wants to output before its downstream component has output, it stalls for one minimum time unit, waiting for downstream space before outputting.

Hence the following component-output computation proposition (incomplete): components push downstream during computation rather than pulling from upstream.

Combining this with the observed “4, 1s stall”: four minimum time units equal 1s, so the minimum time unit is 1/4s. The smallest displayed time is 1s; 4 intervals of 1/4s must accumulate before 1s appears on screen, producing the apparent “4, 1s stall.”

Time units: minimum time unit 1tick = 1/4s; minimum server-data communication (displaying a difference) interval 1s = 4tick; minimum belt distance x = 1tick / (2s/tile) = 1/8 tile.

To explain why the upstream component computes first, we must know how the game orders components. It assigns layers to logistics components using BFS from downstream toward upstream. Smaller layer numbers are usually downstream. Within each layer, output is computed in a placement-like order; each component outputs when its turn is reached.

Layering theory (incomplete): the game assigns layers to logistics components using a downstream-to-upstream BFS algorithm. Smaller layers are usually downstream; within each layer, output is computed in a placement-like order. This is essentially equivalent to damping.

Layering usually gives downstream components smaller numbers, but BFS can also give a downstream component a larger number. The upstream component then computes first: this is why the structure above stalls.

Why does n appear in the formula? A reasonable inference is that upstream output fails only when all n downstream item positions are filled and upstream/downstream items align. For “upstream can always output when downstream is not full” to hold, downstream internal items must move before upstream items during output. This gives the induce–transfer–move model.

Induce–transfer–move: when computing, a component first induces movement of items inside its downstream component, then transfers its own items downstream, and finally moves its own internal items.

Under this model, consider upstream 0x → downstream 0x,0x,X (two items about to transfer and one empty position, with downstream to the right; 7x~0x indicate positions, 7x just entering a tile, 0x about to leave, and X an empty tile). First downstream becomes X,7x,7x, then upstream 0x transfers to downstream 7x: no stall while downstream is not full. With 0x → downstream 0x,0x, induced movement cannot push downstream items further, transfer fails, and upstream stalls for 1tick.

Input, Output, and Merge Priority ​

Next consider another common practical phenomenon: merge priority.

Simple experiments suggest that earlier-placed upstream components of a Converger compute first.

Merge priority (incomplete): earlier-placed upstream components enter a Converger first.

Merge priority: after a Converger computes, if the first upstream component to compute is not a Splitter, items enter by round-robin servicing among that Converger's non-Splitter upstream components. If the first is a Splitter, its items enter first.

What determines earlier computation? A smaller layer number, or an earlier position within the same layer. (The within-layer ordering is explained later; for now, assume earlier placement means earlier computation.)

Why? Naturally, the first to compute outputs into the Converger and occupies its space first. To implement round-robin merging while keeping the Converger responsible only for output computation, its upstream components must select the round-robin input when computing their own output. But Splitters also need round-robin output code, so this input-selection code was omitted. We can therefore extend the component-output computation proposition: components output during their computation. A non-Splitter attempting to output into a Converger also makes that Converger's other non-Splitter upstream components output; the Converger's round-robin counter determines which is accepted. A Splitter attempts to choose its output direction according to its own round-robin counter.

Factories show a similar phenomenon. Because their storage capacity far exceeds a Converger's, and this has little to do with merging, it is called input priority.

Input priority: the first input component to compute has priority; when a non-Splitter has priority, service rotates among non-Splitters.

Although factory inputs resemble Convergers, another phenomenon shows that factory outputs differ greatly from Splitters.

Simple experiments give:

Output priority: among components directly connected to a factory output, smaller layer numbers have higher priority; non-Convergers share the lowest priority. If the highest-priority component is not a Converger, service rotates among non-Convergers. With equal layers, the one connected to its upstream first has priority.

Why does output priority occur? First we need a factory-output computation proposition for normal factory output: to rotate output normally, without Splitter-like output lag, a factory tracks every downstream non-Converger component and computes its output after they have all computed. However, as an upstream source of a Converger, it outputs immediately because of the component-output proposition, rather than waiting for higher-layer non-Convergers to output. Naturally, it then does not rotate output among non-Convergers.

Depot Unloaders and Reactor Crucible outputs use entirely different logic: they wait until the entire logistics system finishes before outputting, so the above round-robin behavior does not affect them.

One special case mentioned here is priority for the earlier upstream connection when layers are equal. Again, because of the component-output proposition, the Converger's other upstream components (clearly in the same layer as the factory output) also make the factory output when they compute. (The exact within-layer order is discussed later.)

Output priority is a convenient tool for checking component layers, and an important part of constructing priority-based lines.

Introducing Terminal Order ​

When using water pipes, people often say “a one-tile pipe stalls water.” After learning about output lag, a connection is easy to imagine: studying examples shows that changing downstream placement order sometimes removes the problem. Switch to belts for a more visible test.

Here a Control Port set to 6/min simulates “liquid consumption only 0.5/s with input at 2/s.” Merge downstream outputs to observe phase conveniently.

Building it shows output lag at the first Splitter: some items align with the belt arrows and some do not, indicating that the Splitter's layer is smaller than the belt's. Next use output priority to observe layer changes more easily.

Changing placement order of the two downstream stashes changes the Splitter's layer. Therefore not all furthest-downstream components enter the initial BFS layer together. Even connected components may need several BFS passes to complete layering.

This requires a special ordered data structure whose entries each contain multiple components, forming the initial layer of one BFS. Since it stores downstream terminal components, we call it terminal order.

What is a terminal? As shown, it is a logistics component next to a factory input.

Terminal component: a logistics component connected to a factory input. Exceptionally, a Splitter with another earlier-connected Introduction to Analyzing Endfield Logistics Bugs is not a terminal component. As a further exception, a logistics component with no output can also be regarded as a factory; this does not count as a factory in the preceding exception.

Terminal order: when a logistics component connects downstream and becomes a terminal component, it joins the terminal order. If a group of other terminal components with the same downstream factory already exists, it joins that group; otherwise it forms a new group at the end. Exceptionally, a Splitter joining terminal order does not merge into another group, but goes at the end. Naturally, a component leaves terminal order when deleted or no longer terminal.

That may be convoluted. An equivalent description is: sort terminal components by the order in which they connected to factories; then, for each factory, merge its non-Splitter terminal components into a group at the position of the earliest one. This describes the result rather than the process.

Each terminal-order entry starts one layering BFS. Different passes start with the same layer number, and a pass does not overwrite previous results or terminal components.

When a Splitter is upstream of a Converger, it may have other downstream components, so its layer need not equal “Converger layer + 1.” Merge priority must then be analyzed case by case.

Output Lag under Terminal Order ​

The terminal-component definition mentioned that outputless logistics components may be treated as factories in terminal-order calculations. This gives a very convenient output-lag structure.

Place components 0 and 1 first to create a very early terminal-order entry. Connecting factory inputs later in the >0 direction then guarantees Splitter output lag.

We can now solve the earlier “one-tile pipe” problem too.

Replace the red-boxed components (the “components near the upstream end of the Splitter chain”; moving/replacing is equivalent to disconnecting/reconnecting). Their associated downstream-factory terminal entries move to the back, letting the Splitter's layer be computed at its highest possible value and eliminating stalls.

This simple output-lag structure conveniently constructs 4n/(4n+0.5)=8n/(8n+1) rate limiters. Familiar denominators include n=3→25=55, n=6→49=77, and n=9→73. Their uniformity even exceeds the conventional upper limit defined through sequences.

Computation Order within a Layer ​

Repeatedly replacing components as above can reveal a special case.

Ordinarily, a later-placed Splitter should compute after the 2 Belt Bridges and cause no output lag. In practice, however, replacing belt 1 in this situation still produces lag.

Actually, within one layer, the logistics component with the earlier downstream connection computes first. Also, placement always connects upstream before downstream.

In most cases this nearly equals placement order, so placement order is sometimes used directly. This can usually be treated as a special case. Only with terminal order and within-layer ordering added is layering theory complete. Layering theory, the two output-computation propositions, the induce–transfer–move model, and the time unit together form the basic logic of logistics-network computation.

Brief Analysis of Merge-Priority/Output-Priority Overflow after Output Lag ​

In this structure, after lag is triggered, each passing Originium item should incur one minimum time unit of stall. Why does priority merging not alternate one Ferrium Ore with one Originium Ore?

Observation shows that Ferrium Ore entering the merge stops the lag structure's output. At that moment, both the belt downstream of its Splitter and the next downstream Splitter hold one Originium Ore each. The Splitter triggers output lag, delaying its internal Originium Ore by 1tick. The resulting gap lies behind those first two Originium Ore items, and Ferrium Ore enters that gap. Thus the pattern is two Originium Ore, one Ferrium Ore.

This structure gives upper 3:lower 1 output after lag. Why?

Observation shows that when Originium Ore reaches the belt downstream of the Splitter, three Originium Ore items have entered the upper route. The Splitter then tries to output again, triggering lag. The upper priority route cannot accept another item, so incoming items use the next-priority downstream route. Because the lag structure also has one empty tile, lag between the previous three Originium Ore items does not affect the next round's input.

This structure combines several factors to produce a logistics bug. Preliminary experiments give two results, shown below. (Control Ports conveniently control whether a route flows and separate some upstream/downstream sections.)

The left Splitter does not split: “splitting failure.” The right Splitter splits and blocks the Converger's other upstream input: “successful splitting.” Analyze the cases below.

First, analyze layers for different terminal orders.

When the lower-right terminal is earlier in terminal order (equivalent to replacing the Splitter's downstream stash):


Merge priority occurs; splitting succeeds when the Splitter is placed first.

[0] When the upper-right terminal is earlier in terminal order:


Within-layer computation order must be considered.

	When the Converger is placed before the Splitter:

		[1] If the Splitter is placed (connected) before the belt downstream of the Converger, the Splitter computes first.

Brief Analysis of Avoiding Output Lag ​

I. Lag occurs because one Splitter output has a smaller layer and another a larger layer, while the Splitter's layer is computed along the smaller-layer route.

  1. Modify terminal order so that the Splitter is layered along the larger-layer route.
  2. Where terminal order cannot be kept stable (for example, saving a blueprint), make both routes equally high-layered. Whichever route determines the Splitter's layer, it will no longer be smaller than its downstream component's layer.
  3. Add a Protocol Stash/Fluid Tank or similar device on the higher-layer route. It interrupts layer calculation and lowers that layer, achieving b.

II. Lag requires the Splitter to attempt another output after its downstream section fills.

  1. Extend downstream components to increase storage. If they can hold all consecutive input, lag does not occur. Alternatively, regard the lag structure as an 8n/(8n+1) limiter and raise n to increase maximum throughput; total flow can then stay unchanged even if lag occurs.
  2. Give the Splitter several output directions filtered for the same material, then merge them. Each downstream route receives less than half the input, does not fill, and naturally avoids lag.

Readers can consider other ways to avoid the problem. These are only methods the author has seen, not an exhaustive list.

Pipe Transport and Special Factories ​

Compared with belts, pipes have special properties:

  • Two different liquids cannot occupy the same pipe simultaneously.

  • The minimum pipe distance is 1/2 tile. This makes liquids 4 times faster than solids and changes output-lag behavior slightly.

Everything else is currently considered identical. For qualitative lag studies, or single-liquid cases, belts can usually substitute for pipes for visualization.

Compared with other factories, (Expanded) Reactor Crucibles, Depot Loaders/Unloaders, and the Protocol Automation-Core are special, perhaps because of their output-selection modes. Their inputs may switch unpredictably between priority and round-robin input; even two non-Splitters do not always alternate. Crucible outputs follow component-like rather than factory-like round-robin logic; Unloaders and the Core unpredictably show priority or round-robin behavior. Convergers touching their outputs show special merge priority: crucibles always have low merge priority. Crucibles and Unloaders stop outputting when switched off (Unloaders previously had no switch, lol).

Purification Unit outputs map recipes to fixed output ports; one port cannot output every liquid, so output priority naturally does not occur.

Factory operation is currently considered to follow this logic:

Factory operation: within 1tick, execute (logistics network and factory input/output) → finish production → start production. Since output is at least layer 2 and input depends on layer 1, factory input is always considered earlier than output.

Production takes 1tick less than its described duration.

The 1tick Stall in Blocking Propagation ​

When a stash/Fluid Tank is full, a blocking signal passing through it is delayed by 1tick. Specifically, downstream changes from blocked to flowing, but the Protocol Stash cannot accept input because it has no space. Only after it outputs on the next 1tick can input succeed and the empty slot pass through. This is usually insignificant: even with this 1tick delay, output once every n-tick generally still means input once every n-tick. Series-connected stashes show the accumulated delay (1tick per stash).

Reaction versus Output Priority in Reactor Crucibles ​

This section currently has unresolved problems and may yield unstable results.

The current view is that, during operation, the Reactor Crucible may cycle through each recipe, checking whether it can finish and whether it can start. The recipe-checking order may be related to the order shown in the recipe list.

Incoming items usually leave immediately because the crucible's input precedes output: within the same 1tick, material is output immediately after entering, without remaining until the production-start stage, so production naturally never starts.

Newly produced Liquid Xiranite is immediately used to produce Xircon Effluent because production completion is immediately followed by production start, before the output stage.

Sewage produced by the Xircon reaction prioritizes output because the Xircon reaction follows the Xircon Effluent reaction. The Sewage passes through the output stage before reaching the start stage of the Xircon Effluent reaction.

When reaction results are full, and external input and production results simultaneously try to enter the crucible while it attempts to output one drop, the production result outputs first. This follows naturally from the above order: output and recipe completion occur in the same tick, while this input takes effect only on the next tick.

Side-Priority Phenomenon of Depot Unloaders and Reactor Crucibles Connected to a Converger's Side ​

As covered in Introduction to Analyzing Endfield Logistics Bugs, Depot Unloaders and Reactor Crucibles always wait until all the Converger's other routes have finished computing before outputting. If the Converger at their outlet has other inputs, those inputs naturally enter first, so the Unloader or Crucible cannot output into the Converger: the other inputs take priority, and the Unloader or Crucible has secondary priority.

Appendix ​

These are not considered bugs. But having read this far, perhaps you want to write a perfect simulator, in which case you may want to know them.

Output round-robin order ​

Two kinds of round-robin servicing follow different logic.

Component round-robin logic: always follows connection order, skipping a port that cannot output. There is no output priority. Before anything has output, it starts with the second-connected component. Factory input also follows component round-robin logic.
Factory round-robin logic: follows the order of longest time since last output. A port unable to output is checked first next time. Output priority exists. Before anything has output, it follows connection order.

Input ordering cannot currently be confirmed rigorously; in some cases priority problems appear for no apparent reason.

Connection order when placing components ​

It is believed to connect upstream first, then downstream, attempting connections counterclockwise.

Blueprint placement order ​

Saving a blueprint is believed to place belts/pipes later. The order of other factories/components cannot normally be determined; with only two factories/components or two belts, selection order is saved. Placement is believed to follow saved order: the same blueprint produces only one result. But saved order cannot be stabilized, so only later belt/pipe placement is guaranteed.

Simply put, when saving, belts/pipes come after everything else; other ordering is indeterminate. Placement order + selection order affect saved order. Once saved, it changes almost never, and is nearly equivalent to placement order (however, because the saved blueprint lives on Hypergryph's servers rather than locally, we cannot confirm whether the relationship between saved order and placement order changes afterward).
